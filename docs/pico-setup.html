Pico 2 H servo controller

The Pi 5 sends text commands over USB to a Raspberry Pi Pico 2 H. The Pico drives the servos from its own hardware PWM, keeps every servo inside its limits, and lets go of all of them when the Pi goes quiet. The servos run from a separate 5 V supply.

Planned: guide written, not built yet Decision D17 Protocol v1 · /dev/buddy-pico

Wiring

USB signal 3.3 V (orange lead) servo 5 V (red lead) ground (brown lead) must stay unconnected

Electrical rules

Servo 5 V never meets the Pi

Nothing from the servo rail goes to Pico pin 39 or 40. Two servos starting together pull ~1.5 A, which would brown out the Pi's 1.6 A USB budget.

Grounds are shared

Supply −, servo GND and Pico pin 3 meet on one rail. Without a common reference the servos jitter or ignore the signal.

Capacitor at the servos

1000 µF covers the current spikes the long supply lead can't. It is polarised: the stripe leg goes to GND.

Power order

On: Pico USB first, then the servo supply. Off: servo supply first. Check polarity with the multimeter before the first connect.

Firmware behaviour

C++ on Pico SDK 2.3.1 in skeleton/firmware/pico/, a separate CMake project built on the Pi. The protocol header shared/include/buddy/motion_protocol.hpp is shared with the motion service.

TopicBehaviour
PWM150 MHz / 150 = 1 µs tick, wrap 19 999 → 50 Hz. The compare value is the pulse width in µs.
BootAll channels off. A channel needs LIMIT before it accepts MOVE.
LimitsPer channel, inside a hard 500–2500 µs. Moves outside are clamped and the reply says so.
RampsLinear to the target over ms, updated every 20 ms.
Link watchdogNo line for 2 s → all servos relaxed (limp), * RELAXED link.
HW watchdog500 ms. A firmware hang reboots the Pico with all channels off.

Protocol v1

ASCII lines over USB CDC. Every request starts with an id (1–65535) that the reply echoes. Lines starting with * are unsolicited events.

RequestReply
id HELLOOK buddy-motion <fw> 1
id LIMIT ch min maxOK, enables, doesn't move
id MOVE ch us msOK / OK clamped us
id RELAX ch|*OK
id PINGOK, every 500 ms from the service
errorsERR bad-channel|no-limit|bad-args|unknown
events* DONE ch us · * RELAXED link · * BOOT fw

Build order

  1. Check the supply

    Multimeter on V⎓: 5.0–5.3 V between the socket's + and − wires. −5 V means swapped polarity.

  2. Wire the breadboard

    As in the diagram. Before power: continuity check that servo + and Pico 39/40 are not connected, rail − and Pico pin 3 are.

  3. Set up the Pi

    setup.sh pico: arm-none-eabi GCC, picotool 2.3.1 in /opt/picotool, picocom, udev rule for /dev/buddy-pico.

  4. Build and flash

    deploy/deploy.sh --firmware. First flash: hold BOOTSEL while plugging in. Later flashes reboot the Pico via picotool load -x -f.

  5. Test by hand

    picocom session above, then the load test with vcgencmd get_throttled and the multimeter on the servo rail.

Done when

  • MOVE sweeps a servo, and a move past its limit is clamped, not executed.
  • With no input for 2 s, every servo goes limp.
  • While both servos move under load, vcgencmd get_throttled stays 0x0 and the servo rail stays ≥ 4.8 V.
  • deploy/test.sh --pi -R MotionProtocol passes.
